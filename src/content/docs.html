Documentation

Running ferrite

From the first install to a second box. The panel does almost everything here; the config snippets show what it writes, for when you'd rather edit the file.

Install

Ferrite is one binary plus the panel's static files. Pick whichever way of running it suits the box.

Install script (Linux)

Downloads the latest server and panel, checks their checksums, installs them under /var/lib/ferrite and registers a systemd or OpenRC service. On Debian and Ubuntu it also turns off the systemd-resolved stub listener, which otherwise holds port 53. Read it first if you like: 

curl -fsSLO https://raw.githubusercontent.com/syntlyx/ferrite-server/main/install.sh
less install.sh
sudo sh install.sh

The service runs as its own ferrite user with the capabilities to bind port 53 and to run kernel WireGuard, not as root. Running the script again updates an install.

Docker

The image is on GitHub Container Registry. Use the host network: profiles and routing rules match each device by its address, and behind a Docker bridge every query arrives from the gateway. 

services:
  ferrite:
    image: ghcr.io/syntlyx/ferrite-server:latest
    container_name: ferrite
    restart: unless-stopped
    network_mode: host
    cap_add: [NET_BIND_SERVICE]
    volumes:
      - ferrite-data:/var/lib/ferrite
volumes:
  ferrite-data:

Mount /var/lib/ferrite so the config, history and updates survive the container. Add NET_ADMIN to cap_add if you want the kernel WireGuard backend; the wireguard module must then be loaded on the host. If you must use a bridge, set FERRITE_PANEL_IP to the host's LAN address so fe.te resolves, and publish 443/tcp as well if you route through tunnels.

Static binary

Every release has musl builds for x86_64 and aarch64, each with a .sha256 next to it: 

VER=v0.2.0; ARCH=$(uname -m)-unknown-linux-musl
BASE=https://github.com/syntlyx/ferrite-server/releases/download/$VER
curl -fsSLO $BASE/ferrite-$VER-$ARCH.tar.gz
curl -fsSL  $BASE/ferrite-$VER-$ARCH.tar.gz.sha256 | sha256sum -c -
tar -xzf ferrite-$VER-$ARCH.tar.gz && sudo install -m755 ferrite /usr/local/bin/ferrite

From source

cargo build --release
sudo cp target/release/ferrite /usr/local/bin/ferrite

On Unraid, use the template from Community Apps. It runs the same image.

Point your network at it

Ferrite only filters the devices that ask it. The usual way to get there is the router:

  1. Open your router's DHCP settings and set the DNS server to the ferrite box's address.
  2. Leave the second DNS field empty, or put a second ferrite there. A public resolver as the second server means devices sometimes use it and skip filtering.
  3. If the router hands out an IPv6 DNS server too, point that at ferrite or turn it off. Otherwise IPv6-capable devices keep asking the router.
  4. Devices pick up the change with their next DHCP lease. Reconnecting to Wi-Fi does it at once.

Browsers with their own "secure DNS" setting bypass any network DNS filter. Set it to use the system resolver, or turn it off.

You can also set the DNS server by hand on a single device, which is a good way to try ferrite before switching the whole network.

Open the panel

Go to http://fe.te from any device that uses ferrite. It is a built-in record pointing at the box. From a device that doesn't, use the box's address instead.

Set a password on the box before anything else:

ferrite passwd

Without a password or an API key the panel is open to anyone who can reach it, and ferrite warns about that in its log. A fresh binary with no config listens on 127.0.0.1:8080 only; the install script and the Docker image put the panel on port 80 of the network.

To check that filtering works, ask for a known ad domain. The answer should be empty, and the query shows up in the log with your device's name: 

dig @<ferrite address> doubleclick.net

Device names

Ferrite learns names from your router (reverse lookups), from mDNS and from the neighbour tables. For reverse lookups to work it must know which questions go to the router: 

ferrite setup

detects your gateway, subnet and local search domain and writes the matching local zones. Any device can also be named by hand in the panel; a name given by MAC follows the device across address changes. 

[[client_aliases]]
mac  = "aa:bb:cc:dd:ee:ff"
name = "Kitchen TV"

Blocklists and allowlists

Subscribe to lists from the built-in catalog or by URL (StevenBlack, OISD, AdGuard, Hagezi and the like). Hosts, Adblock (||domain^) and plain one-domain-per-line formats are detected on their own and compiled into one compact lookup. Lists are refreshed twice a day, and only downloaded again when they changed.

Allowlists work the same way in reverse: subscribe to a community false-positive list and its domains are never blocked. In Adblock-format lists, @@||domain^ exceptions count as allow entries. 

[[blocklist.lists]]
name    = "StevenBlack"
url     = "https://raw.githubusercontent.com/StevenBlack/hosts/master/hosts"
enabled = true

[[allowlist.lists]]
name    = "anudeepND Whitelist"
url     = "https://raw.githubusercontent.com/anudeepND/whitelist/master/domains/whitelist.txt"
enabled = true

A list can also be a local file: url = "file:///etc/ferrite/custom.hosts".

Your own entries

Block and allow entries take three forms:

Entry Matches
ads.example.com the name and every subdomain
*.example.com subdomains only, not example.com itself
/^ads?[0-9]+\./ a regular expression, anywhere in the name, ignoring case

An allow entry beats every list. Add one straight from the query log when a list goes too far.

Services and SafeSearch

The service catalog groups the domains behind 43 apps in seven categories (video, music, social, messaging, gaming, AI and shopping), so blocking TikTok or Roblox is one switch instead of a list of domains. Services can be blocked for the whole network or only in a profile.

SafeSearch sends Google, Bing and DuckDuckGo to their safe hosts, so results are filtered whatever the browser says. YouTube Restricted Mode can be moderate or strict. A profile can make both stricter for its devices, never looser. 

[blocklist]
services = ["tiktok"]
safe_search = true
youtube_restricted = "moderate"   # off | moderate | strict

What a blocked name gets

Mode Answer
nxdomain no such name (the default); apps give up at once
nodata the name exists, without this record type
null_ip 0.0.0.0 for A, :: for AAAA
custom_ip an address of yours, such as a block page on your network
refused the server declines to answer

Why was it blocked?

Click any domain in the query log or on the dashboard. The side panel says which list, entry or service matched, which allow entry exempted it if one did, and which profile was in charge. Tools has the same check for a name you type, along with a DNS lookup through your own upstreams, a DNSSEC check, WHOIS, and certificate and reachability probes.

Pausing and bypass

Filtering can be paused for 5, 30 or 60 minutes for the whole network, from the sidebar, or for one device, from Clients. It comes back on its own. A device can also skip filtering for good: 

[blocklist]
client_bypass = ["192.168.1.50", "aa:bb:cc:dd:ee:ff"]

Profiles

A profile is a set of rules for chosen devices, picked by MAC or IP. It can block services, use only some of the lists, add its own block and allow entries, force SafeSearch, run on a schedule, or flip to allowed-only. Devices in no profile follow the network-wide rules.

For a device in a profile, a name is checked in this order:

  1. the profile's own allow and block entries, and its services
  2. the allowlists
  3. allowed-only, if the profile has it on
  4. the network-wide entries, services and lists
[[blocklist.profiles]]
id = "kids"
name = "Kids"
clients  = ["aa:bb:cc:dd:ee:01", "aa:bb:cc:dd:ee:02"]
services = ["tiktok", "roblox", "fortnite"]
safe_search = true
youtube_restricted = "moderate"

Schedules

A profile with no time windows is always on. Add windows and it applies only inside them; outside, its devices follow the network-wide rules. Times are the box's local time, and a window may cross midnight. 

[[blocklist.profiles.schedule]]
days = ["sun", "mon", "tue", "wed", "thu"]
from = "21:30"
to   = "07:00"

Allowed only

For devices that should reach only a few places, such as a camera, a robot vacuum or a kid's first tablet, a profile can block everything that isn't explicitly allowed. Local names keep working without extra setup: reverse lookups, .lan, .local and your local zones. 

[[blocklist.profiles]]
id = "iot"
name = "IoT"
clients      = ["aa:bb:cc:dd:ee:ff"]
default_deny = true

How routing works

When a domain matches a routing rule, ferrite answers the DNS query with its own LAN address, so the device connects to ferrite. Ferrite reads the hostname from the TLS SNI (port 443) or the HTTP Host header (port 80), checks the rule again against it, and passes the connection through the rule's egress. It never terminates TLS: the device still checks the site's real certificate.

Routing decides how traffic leaves; blocking still decides whether a name resolves. A tracker under a routed service stays blocked unless you allow it. Rules, egresses and ports reload without a restart.

Routing needs ports 80 and 443 on the box. The panel shares port 80 and is told apart by the Host header.

Egresses

Kind What it does
direct connects straight out, resolving through ferrite's own upstreams
socks5 through a SOCKS5 proxy, hostname included. Point it at a local Tor (127.0.0.1:9050) to go over Tor
wireguard built-in WireGuard from a pasted .conf; routed names resolve through the tunnel too
evasion like direct, but splits the TLS ClientHello at the SNI across TCP segments, so DPI can't read the hostname

WireGuard

Paste the .conf your VPN provider gives you. Ferrite picks one of two backends per host and says which in its startup log:

  • Kernel (preferred, Linux): a real WireGuard interface with policy routing; your main routing table is never touched. The kernel does the crypto on all cores. Needs CAP_NET_ADMIN and the wireguard module.
  • Userspace (everywhere else): fully inside the process, no extra capability and no TUN device. Fine for browsing, slower for streaming at full speed. 
[[proxy.egresses]]
id = "nl"
name = "NL"
enabled = true
kind = "wireguard"
# backend = "kernel"    # auto by default; "kernel" fails loudly instead of falling back
config = """
[Interface]
PrivateKey = <your key>
Address = 10.2.0.2/32
DNS = 10.2.0.1
[Peer]
PublicKey = <peer key>
Endpoint = 203.0.113.10:51820
AllowedIPs = 0.0.0.0/0
"""

WireGuard's encryption is plain CPU work, and small ARM boards have no hardware for it. Expect a few hundred Mbit/s through a tunnel on that class of board, whatever its port speed.

Rules

A rule sends a domain or a whole catalog service through an egress, for every device or only for some. A plain domain covers its subdomains; *.example.com covers only the subdomains. With fail-closed on, a rule whose egress is down refuses the connection instead of letting it go out directly. 

[[proxy.rules]]
pattern = "example.com"
egress  = "nl"
fail_closed = true
clients = []           # empty = every device; or IPs and MACs

[[proxy.rules]]
service = "netflix"
egress  = "nl"

Upstreams

Ferrite forwards what it can't answer to a pool of upstream resolvers, round-robin with failover. Plain, DoT, DoH and DoQ can be mixed. The install script starts you on Cloudflare over DoH. 

[[upstream]]
type = "https"
url  = "https://cloudflare-dns.com/dns-query"
bootstrap_ip = "1.1.1.1"

[[upstream]]
type = "tls"
address  = "1.1.1.1"
port     = 853
tls_name = "cloudflare-dns.com"

[[upstream]]
type = "quic"
address  = "94.140.14.14"
port     = 853
tls_name = "dns.adguard-dns.com"

DoH needs bootstrap_ip when ferrite is the box's own resolver, since it can't look up the DoH host through itself. A plain or DoT upstream can go through a tunnel with egress = "<id>", falling back to direct while the tunnel is down. Outgoing queries have EDNS Client Subnet stripped and ask for DNSSEC.

Local zones

Names only your router knows, such as reverse lookups for 192.168.x.x or printer.lan, should go to the router rather than the public upstreams. Zones match by suffix and the longest one wins. ferrite setup writes them for you. 

[[zones]]
name     = "1.168.192.in-addr.arpa"
upstream = "192.168.1.1:53"

[[zones]]
name     = "lan"
upstream = "192.168.1.1:53"

Local records

A, AAAA and CNAME records of your own answer before anything else, exact or wildcard. 

[[custom_records]]
domain = "nas.lan"
type   = "A"
value  = "192.168.1.20"

[[custom_records]]
domain = "*.home.lan"
type   = "A"
value  = "192.168.1.100"

Cache

Answers are cached, with upstream TTLs clamped between min_ttl and max_ttl. The optimistic cache answers a name from an expired entry at once and refreshes it in the background, so devices don't wait on the upstream, and names keep resolving for a while when the upstream is down. 

[dns]
cache_size    = 10000
min_ttl       = 60
max_ttl       = 3600
serve_stale   = true
stale_max_age = 43200   # seconds an expired answer may still be served

Password and access

A browser stays signed in for 7 days after it was last used, across restarts and updates. Settings, then Access, lists the signed-in browsers and signs any of them out; changing the password signs out all the others.

Scripts use an API key, sent as Authorization: Bearer <key> or X-Api-Key: <key>. See the API reference.

You can also limit who may use the resolver, and how fast:

[dns]
rate_limit      = 1000                 # queries per minute per device; over it, REFUSED
allowed_clients = ["192.168.1.0/24"]   # only these get answers
denied_clients  = ["192.168.1.66"]     # these never do

Privacy and storage

Everything you set lives in config.toml. The database only holds what ferrite observed: the query log, its rollups, the device inventory and the panel's sessions.

  • Retention: the query log keeps 30 days by default (log_retention_days), and can be capped in megabytes too (log_max_mb).
  • RAM only: backend = "memory" keeps history in a bounded ring in memory; nothing about your traffic is written to disk, and it is gone after a restart.
  • Switches: the query log and the statistics can each be turned off. With both off ferrite keeps filtering and records nothing about what was resolved.
  • Clearing the log also compacts the database, so the space really leaves the disk.

The only call ferrite makes on its own is an hourly check for a new release on GitHub.

Updates

The panel shows when a release is out and updates the server and itself in place; the service manager restarts ferrite on the new binary. A panel release is only offered when it fits the running server. In Docker, restarting the container also fetches the latest release, unless you pin one with the variables below.

Backup and restore

Settings, then System, exports the whole configuration as one file and restores it on this box or another. Copying config.toml does the same. Losing the database loses history and sessions, never your setup.

A second box

A second ferrite can follow the first, so devices given both addresses get the same answers from either. It takes the parts you choose from the primary every few minutes, with the primary's API key, and restarts for about a second when something changed. Edit on the primary: changes made on the follower to those parts are replaced on the next sync. 

[sync]
primary  = "http://192.168.1.10"
api_key  = "<the primary's API key>"
interval = 300
sections = ["filtering", "records", "devices", "dns"]

Add "tunnels" only if the second box routes too, and never with the same WireGuard key on both: two peers with one key knock each other off.

From Pi-hole or AdGuard Home

Settings, then System, reads a Pi-hole v6 Teleporter export or an AdGuardHome.yaml. It shows what comes over (lists, block and allow rules, local records, groups and per-device settings, blocked services) and what can't, and you choose the parts before anything changes.

Notifications

One webhook gets an event when a tunnel has been down for over a minute (and when it recovers), and when a device the box has never seen joins the network. The format fits the receiver: ntfy, telegram, discord, slack (also Mattermost and Rocket.Chat), gotify, or json for Home Assistant and scripts. Settings can send a test event. 

[notifications]
webhook       = "https://ntfy.sh/my-ferrite"
format        = "ntfy"
tunnel_alerts = true
new_device    = true

# Telegram: the bot's sendMessage URL and the chat to post to
# webhook = "https://api.telegram.org/bot<token>/sendMessage"
# format  = "telegram"
# chat_id = "123456789"

Metrics

Prometheus metrics are at /api/metrics, behind the API key when one is set. There is a Grafana dashboard ready to import.

AI assistants

/api/mcp lets an assistant that speaks the Model Context Protocol, such as Claude Code, read what ferrite is doing: why a site is blocked, what a device did. It uses the API key and is off by default. Changes (block, allow, pause) need a second switch. 

[mcp]
enabled       = true
allow_changes = false

Config file

~/.config/ferrite/config.toml for a user install, /etc/ferrite/config.toml system-wide. The panel is the main editor and writes the file itself; hand edits are fine, but comments inside the sections the panel manages don't survive a save. Without a file ferrite starts with plain upstreams and the panel on 127.0.0.1:8080. Every key is described in config.toml.example.

Troubleshooting

Port 53 is already in use

On Debian and Ubuntu, systemd-resolved holds it. The install script turns its stub listener off; by hand, set DNSStubListener=no in /etc/systemd/resolved.conf.d/ferrite.conf and restart systemd-resolved.

Every device shows up as one

Ferrite sees all queries coming from the same address: it is behind a Docker bridge, or the router forwards DNS itself. Run Docker on the host network, and hand ferrite's address out over DHCP rather than setting it as the router's upstream.

Devices show as IP addresses

Reverse lookups aren't reaching the router. Run ferrite setup, or add the local zones by hand.

fe.te doesn't open

The device isn't using ferrite for DNS yet, or ferrite runs in a Docker bridge without FERRITE_PANEL_IP. Use the box's address meanwhile.

A site or app stopped working

Find it in the query log, click the blocked name to see what matched, and allow it. To rule ferrite out quickly, pause filtering for that one device.

Tunnels are slow on a small board

Check the startup log for the WireGuard backend. If it says userspace, give ferrite CAP_NET_ADMIN and load the wireguard module. With the kernel backend the limit is the CPU's encryption speed, not ferrite.
