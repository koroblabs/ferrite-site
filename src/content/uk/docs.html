Документація

Робота з ferrite

Від першого встановлення до другого боксу. Майже все тут робиться в панелі, а фрагменти конфігу показують, що саме вона записує, якщо вам зручніше редагувати файл.

Встановлення

Ferrite — це один виконуваний файл плюс статичні файли панелі. Виберіть спосіб запуску, що пасує вашому боксу.

Скрипт встановлення (Linux)

Завантажує найновіші сервер і панель, перевіряє контрольні суми, встановлює їх у /var/lib/ferrite і реєструє сервіс systemd чи OpenRC. На Debian і Ubuntu він також вимикає stub listener у systemd-resolved, який інакше займає порт 53. Можете спершу прочитати скрипт: 

curl -fsSLO https://raw.githubusercontent.com/syntlyx/ferrite-server/main/install.sh
less install.sh
sudo sh install.sh

Сервіс працює від власного користувача ferrite з дозволами займати порт 53 і запускати WireGuard у ядрі, а не від root. Повторний запуск скрипта оновлює встановлення.

Docker

Образ лежить у GitHub Container Registry. Використовуйте мережу host: профілі й правила маршрутизації впізнають пристрій за адресою, а за Docker bridge кожен запит приходить від шлюзу. 

services:
  ferrite:
    image: ghcr.io/syntlyx/ferrite-server:latest
    container_name: ferrite
    restart: unless-stopped
    network_mode: host
    cap_add: [NET_BIND_SERVICE]
    volumes:
      - ferrite-data:/var/lib/ferrite
volumes:
  ferrite-data:

Змонтуйте /var/lib/ferrite для конфігу, історії й оновлень, щоб вони переживали контейнер. Додайте NET_ADMIN у cap_add для WireGuard у ядрі; тоді модуль wireguard має бути завантажений на хості. Якщо без bridge ніяк, задайте FERRITE_PANEL_IP адресою хоста в локальній мережі, щоб fe.te резолвився, і опублікуйте 443/tcp теж, якщо користуєтесь тунелями.

Статичний файл

Кожен реліз має musl-збірки для x86_64 і aarch64, кожна з .sha256 поруч: 

VER=v0.2.0; ARCH=$(uname -m)-unknown-linux-musl
BASE=https://github.com/syntlyx/ferrite-server/releases/download/$VER
curl -fsSLO $BASE/ferrite-$VER-$ARCH.tar.gz
curl -fsSL  $BASE/ferrite-$VER-$ARCH.tar.gz.sha256 | sha256sum -c -
tar -xzf ferrite-$VER-$ARCH.tar.gz && sudo install -m755 ferrite /usr/local/bin/ferrite

З коду

cargo build --release
sudo cp target/release/ferrite /usr/local/bin/ferrite

На Unraid скористайтеся шаблоном з Community Apps. Він запускає той самий образ.

Направте на нього мережу

Ferrite фільтрує тільки ті пристрої, що до нього звертаються. Зазвичай це налаштовують на роутері:

  1. Відкрийте DHCP-налаштування роутера й вкажіть адресу боксу з ferrite як DNS-сервер.
  2. Друге поле DNS залиште порожнім або вкажіть там другий ferrite. Публічний резолвер другим сервером означає, що пристрої часом ходитимуть до нього й оминатимуть фільтрацію.
  3. Якщо роутер роздає ще й IPv6 DNS, направте його на ferrite або вимкніть. Інакше пристрої з IPv6 і далі питатимуть роутер.
  4. Пристрої підхоплять зміну, коли наступного разу отримуватимуть адресу по DHCP. Перепідключення до Wi-Fi робить це одразу.

Браузери з власним налаштуванням «безпечного DNS» оминають будь-який мережевий DNS-фільтр. Налаштуйте їх на системний резолвер або вимкніть цю опцію.

DNS-сервер можна вказати й вручну на одному пристрої. Це добрий спосіб спробувати ferrite, перш ніж перемикати всю мережу.

Відкрийте панель

Відкрийте http://fe.te з будь-якого пристрою, що користується ferrite. Це вбудований запис, що вказує на бокс. З пристрою, що ним не користується, відкрийте адресу боксу.

Перш за все задайте пароль на боксі:

ferrite passwd

Без пароля чи API-ключа панель відкрита всім, хто до неї дістанеться, і ferrite попереджає про це в лозі. Новий файл без конфігу слухає тільки 127.0.0.1:8080 — а скрипт встановлення й образ Docker відкривають панель на порту 80 у мережі.

Щоб перевірити, що фільтрація працює, запитайте відомий рекламний домен. Відповідь має бути порожньою, а запит з'явиться в лозі з іменем вашого пристрою: 

dig @<ferrite address> doubleclick.net

Імена пристроїв

Ferrite дізнається імена від роутера (зворотні запити), з mDNS і з таблиць сусідів. Щоб зворотні запити працювали, він має знати, які питання відправляти роутеру: 

ferrite setup

визначає шлюз, підмережу й локальний домен пошуку і записує відповідні локальні зони. Будь-який пристрій можна назвати й вручну в панелі; ім'я, прив'язане до MAC, лишається за пристроєм, навіть коли змінюється його адреса. 

[[client_aliases]]
mac  = "aa:bb:cc:dd:ee:ff"
name = "Kitchen TV"

Списки блокування й дозволу

Підписуйтесь на списки з вбудованого каталогу або за URL (StevenBlack, OISD, AdGuard, Hagezi тощо). Формати hosts, Adblock (||domain^) і простий список доменів розпізнаються самі й компілюються в один компактний пошук. Списки оновлюються двічі на день і завантажуються заново, лише якщо змінились.

Списки дозволу працюють так само, але навпаки: підпишіться на спільнотний список хибних спрацювань, і його домени ніколи не блокуватимуться. У списках формату Adblock винятки @@||domain^ вважаються записами дозволу. 

[[blocklist.lists]]
name    = "StevenBlack"
url     = "https://raw.githubusercontent.com/StevenBlack/hosts/master/hosts"
enabled = true

[[allowlist.lists]]
name    = "anudeepND Whitelist"
url     = "https://raw.githubusercontent.com/anudeepND/whitelist/master/domains/whitelist.txt"
enabled = true

Список може бути й локальним файлом: url = "file:///etc/ferrite/custom.hosts".

Власні записи

Записи блокування й дозволу бувають трьох видів:

Запис Що охоплює
ads.example.com саме ім'я і всі піддомени
*.example.com тільки піддомени, без самого example.com
/^ads?[0-9]+\./ регулярний вираз, будь-де в імені, без урахування регістру

Запис дозволу сильніший за будь-який список. Додайте його прямо з логу запитів, коли список перестарався.

Сервіси й SafeSearch

Каталог сервісів групує домени 43 застосунків у сім категорій (відео, музика, соцмережі, месенджери, ігри, AI і покупки), тож заблокувати TikTok чи Roblox можна одним перемикачем, а не списком доменів. Сервіси можна блокувати для всієї мережі або лише в профілі.

SafeSearch відправляє Google, Bing і DuckDuckGo на їхні безпечні адреси, тож результати фільтруються, що б не казав браузер. Обмежений режим YouTube може бути помірним або суворим. Профіль може зробити обидва суворішими для своїх пристроїв, але не м'якшими. 

[blocklist]
services = ["tiktok"]
safe_search = true
youtube_restricted = "moderate"   # off | moderate | strict

Що отримує заблоковане ім'я

Режим Відповідь
nxdomain такого імені немає (за замовчуванням); застосунки одразу здаються
nodata ім'я існує, але без такого типу запису
null_ip 0.0.0.0 для A, :: для AAAA
custom_ip ваша адреса, наприклад сторінка блокування у вашій мережі
refused сервер відмовляється відповідати

Чому заблоковано?

Клікніть будь-який домен у лозі запитів чи на дашборді. Бокова панель покаже, який список, запис чи сервіс спрацював, який запис дозволу його звільнив, якщо такий був, і який профіль діяв. В інструментах є та сама перевірка для введеного імені, а також DNS-запит через ваші upstream-сервери, перевірка DNSSEC, WHOIS і перевірки сертифіката та доступності.

Пауза й винятки

Фільтрацію можна поставити на паузу на 5, 30 чи 60 хвилин для всієї мережі (з бокової панелі) або для одного пристрою (на сторінці Clients). Вона вмикається сама. Пристрій також можна назавжди звільнити від фільтрації: 

[blocklist]
client_bypass = ["192.168.1.50", "aa:bb:cc:dd:ee:ff"]

Як утримати пристрої на фільтрі

Деякі пристрої й браузери питають імена деінде, і фільтр їх не бачить. У Settings, далі Network, далі Resolver, для цього є три перемикачі.

  • Firefox перевіряє спеціальне ім'я, перш ніж увімкнути власний DNS over HTTPS. Ferrite відповідає на нього так, щоб Firefox лишався тут. Увімкнено за замовчуванням.
  • iCloud Private Relay відправляє запити Safari в обхід мережі. Вимкнути його для мережі вирішує власник, тому цей перемикач вимкнений, доки ви його не ввімкнете.
  • Encrypted Client Hello ховає ім'я сайту всередині TLS. Ferrite може прибирати його з відповідей, щоб ім'я лишалося видимим. 
[dns]
firefox_canary      = true
block_private_relay = false
strip_ech           = false

Профілі

Профіль — це набір правил для вибраних пристроїв, визначених за MAC чи IP. Він може блокувати сервіси, використовувати лише частину списків, мати власні записи блокування й дозволу, примусово вмикати SafeSearch, працювати за розкладом або перейти в режим «тільки дозволене». Пристрої поза профілями живуть за загальними правилами мережі.

Для пристрою в профілі ім'я перевіряється в такому порядку:

  1. власні записи дозволу й блокування профілю та його сервіси
  2. списки дозволу
  3. режим «тільки дозволене», якщо його ввімкнено в профілі
  4. загальні записи, сервіси й списки мережі
[[blocklist.profiles]]
id = "kids"
name = "Kids"
clients  = ["aa:bb:cc:dd:ee:01", "aa:bb:cc:dd:ee:02"]
services = ["tiktok", "roblox", "fortnite"]
safe_search = true
youtube_restricted = "moderate"

Розклад

Профіль без часових вікон діє завжди. Додайте вікна, і він діятиме тільки в них, а поза ними його пристрої житимуть за загальними правилами. Час рахується за місцевим часом боксу, і вікно може переходити через північ. 

[[blocklist.profiles.schedule]]
days = ["sun", "mon", "tue", "wed", "thu"]
from = "21:30"
to   = "07:00"

Тільки дозволене

Для пристроїв, яким потрібні лише кілька адрес, як-от камера, робот-пилосос чи перший планшет дитини, профіль може блокувати все, що не дозволено явно. Локальні імена працюють без додаткових налаштувань: зворотні запити, .lan, .local і ваші локальні зони. 

[[blocklist.profiles]]
id = "iot"
name = "IoT"
clients      = ["aa:bb:cc:dd:ee:ff"]
default_deny = true

Як працює маршрутизація

Коли домен підпадає під правило маршрутизації, ferrite відповідає на DNS-запит власною адресою в мережі, тож пристрій з'єднується з ferrite. Ferrite читає ім'я хоста з TLS SNI (порт 443) чи заголовка HTTP Host (порт 80), ще раз перевіряє за ним правило і пропускає з'єднання через вихід цього правила. TLS він ніколи не розшифровує: пристрій і далі перевіряє справжній сертифікат сайту.

Маршрутизація вирішує, як трафік виходить назовні, а блокування й далі вирішує, чи резолвиться ім'я. Трекер у сервісі, що йде через тунель, лишається заблокованим, поки ви його не дозволите. Правила, виходи й порти оновлюються без перезапуску.

Телефон із шифрованим DNS можна вести через тунелі й поза домом: увімкніть Away from home too в Tunnels. Тоді домени з правил вказують на публічну адресу бокса, яку ferrite бере із запису імені шифрованого DNS, і порт 443 на ній має вести до бокса. Пропускаються лише ваші пристрої, з адреси, з якої вони щойно питали, і лише для доменів із правил.

Для маршрутизації потрібні порти 80 і 443 на боксі. Панель ділить порт 80, а розрізняють їх за заголовком Host.

Виходи

Тип Що робить
direct з'єднується напряму, резолвлячи через upstream-сервери самого ferrite
socks5 через SOCKS5-проксі, разом з іменем хоста. Направте його на локальний Tor (127.0.0.1:9050), щоб іти через Tor
wireguard вбудований WireGuard з вставленого .conf; імена для тунелю теж резолвляться через нього
evasion як direct, але розбиває TLS ClientHello по SNI на кілька TCP-сегментів, тож DPI не може прочитати ім'я хоста

WireGuard

Вставте .conf від вашого VPN-провайдера. Ferrite вибирає один з двох бекендів для кожного хоста й пише, який саме, в лозі запуску:

  • Ядро ОС (бажано, Linux): справжній інтерфейс WireGuard з policy routing; основна таблиця маршрутизації не змінюється. Шифрує ядро ОС, на всіх ядрах процесора. Потрібні дозвіл CAP_NET_ADMIN і модуль wireguard у ядрі.
  • Userspace (усюди інде): повністю всередині процесу, без додаткових дозволів і без TUN-пристрою. Для сайтів вистачає, для стримінгу на повній швидкості повільніший. 
[[proxy.egresses]]
id = "nl"
name = "NL"
enabled = true
kind = "wireguard"
# backend = "kernel"    # auto by default; "kernel" fails loudly instead of falling back
config = """
[Interface]
PrivateKey = <your key>
Address = 10.2.0.2/32
DNS = 10.2.0.1
[Peer]
PublicKey = <peer key>
Endpoint = 203.0.113.10:51820
AllowedIPs = 0.0.0.0/0
"""

Шифрування WireGuard — це звичайна робота процесора, а малі ARM-плати не мають для нього апаратного прискорення. На платах такого класу розраховуйте на кілька сотень Мбіт/с через тунель, хоч би яка швидкість порту.

Правила

Правило відправляє домен або цілий сервіс з каталогу через вихід, для всіх пристроїв або лише для деяких. Звичайний домен охоплює й піддомени; *.example.com охоплює тільки піддомени. З увімкненим fail-closed правило, вихід якого лежить, відхиляє з'єднання, а не випускає його напряму.

Сайт тягне не лише власне ім'я: CDN, перевірку на бота, шрифти. Якщо вони йдуть повз тунель, сторінка може лишитися білою. У правилі What else the site pulls in показує домени, які пристрої запитували одразу після відкриття сайту, пробує кожен напряму й через тунель і одним натиском пускає в тунель ті, яким він потрібен. 

[[proxy.rules]]
pattern = "example.com"
egress  = "nl"
fail_closed = true
clients = []           # empty = every device; or IPs and MACs

[[proxy.rules]]
service = "netflix"
egress  = "nl"

Upstream-сервери

Те, на що Ferrite не може відповісти сам, він пересилає пулу upstream-резолверів по черзі, з перемиканням при збоях. Plain, DoT, DoH і DoQ можна змішувати. Скрипт встановлення починає з Cloudflare через DoH. 

[[upstream]]
type = "https"
url  = "https://cloudflare-dns.com/dns-query"
bootstrap_ip = "1.1.1.1"

[[upstream]]
type = "tls"
address  = "1.1.1.1"
port     = 853
tls_name = "cloudflare-dns.com"

[[upstream]]
type = "quic"
address  = "94.140.14.14"
port     = 853
tls_name = "dns.adguard-dns.com"

DoH потребує bootstrap_ip у випадку, коли ferrite є резолвером самого боксу, бо інакше не знайде DoH-хост через себе ж. Звичайний чи DoT upstream може йти через тунель з параметром egress = "<id>", а поки тунель лежить, іде напряму. Вихідні запити не містять EDNS Client Subnet і просять DNSSEC.

Локальні зони

Імена, які знає лише роутер, як-от зворотні запити для 192.168.x.x або printer.lan, мають іти до роутера, а не до публічних upstream-серверів. Зони збігаються за суфіксом, і перемагає найдовша. ferrite setup запише їх за вас. 

[[zones]]
name     = "1.168.192.in-addr.arpa"
upstream = "192.168.1.1:53"

[[zones]]
name     = "lan"
upstream = "192.168.1.1:53"

Локальні записи

Ваші власні записи A, AAAA і CNAME, точні чи wildcard, відповідають раніше за все інше. 

[[custom_records]]
domain = "nas.lan"
type   = "A"
value  = "192.168.1.20"

[[custom_records]]
domain = "*.home.lan"
type   = "A"
value  = "192.168.1.100"

Кеш

Відповіді кешуються, а TTL від upstream обмежується між min_ttl і max_ttl. Оптимістичний кеш одразу відповідає з простроченого запису й оновлює його у фоні, тож пристрої не чекають на upstream, а імена ще якийсь час резолвляться, навіть коли upstream лежить. 

[dns]
cache_size    = 10000
min_ttl       = 60
max_ttl       = 3600
serve_stale   = true
stale_max_age = 43200   # seconds an expired answer may still be served

Шифрований DNS

Телефони й ноутбуки можуть звертатися до ferrite шифрованим з'єднанням, удома й поза домом. «Приватний DNS» на Android говорить DNS over TLS. iPhone, Mac і браузери говорять DNS over HTTPS. Кожен пристрій підключається під власним іменем, тож показується під ним у Clients і зберігає свій профіль, де б не був.

Що потрібно

  • Домен, DNS якого на Cloudflare.
  • Ім'я для боксу в ньому, наприклад dns.example.com. Удома ferrite сам відповідає на це ім'я своєю адресою. Щоб користуватися ним поза домом, спрямуйте ім'я та *.dns.example.com на вашу публічну адресу й прокиньте порти 853 і 443 на бокс.

Налаштування

  1. У Cloudflare створіть API-токен із шаблону «Edit zone DNS», обмежений вашою зоною.
  2. У Settings, далі Network, далі Encrypted DNS, увімкніть його, впишіть ім'я, лишіть Let's Encrypt і вставте токен. Ferrite підтверджує ім'я TXT-записом, тож для сертифіката не треба відкривати порт. Він з'являється за хвилину-дві й продовжується сам.
  3. Додайте пристрої в розділі Devices або дайте їм додатися самим (нижче). На Android вставте ім'я пристрою в Налаштування, Мережа, Приватний DNS. На iPhone, iPad чи Mac відкрийте панель на самому пристрої й натисніть Install profile або наведіть камеру на QR-код пристрою. Браузеру потрібна адреса DNS over HTTPS.

DNS over HTTPS ділить порт 443 з тунелями: з'єднання на це ім'я обслуговуються тут, а все інше маршрутизується як раніше. Він працює й через HTTP/3, на UDP 443. Поза домом відповідь отримують лише пристрої зі списку. Ім'я публічне, і бокс не має бути резолвером для кожного, хто його знайде.

Пристрої налаштовуються самі

Телефон удома може відкрити сторінку налаштування в панелі й налаштуватися сам, без пароля: він отримує власне ім'я пристрою й свій профіль, а ви — сповіщення. У Setting up without the password виберіть, кому можна: пристроям, яким ви дали ім'я в Clients (так за замовчуванням), будь-кому вдома чи нікому.

Пристрій, налаштований так або з його панелі в Clients, належить цьому клієнту: це один рядок у Clients, а профіль, пауза й правила тунелів клієнта діють на нього й поза домом.

За зворотним проксі

Якщо зворотний проксі, як-от Nginx Proxy Manager, Caddy чи nginx, передає DNS over HTTPS на бокс, вкажіть його адресу в Reverse proxy. Тоді ferrite вірить клієнту, якого називає проксі: у X-Real-IP чи останньому записі X-Forwarded-For або в заголовку PROXY protocol, коли проксі передає з'єднання цілим, як модуль stream у nginx з увімкненим proxy_protocol. Без цього кожен пристрій виглядає так, ніби він удома. DNS over TLS на 853 має доходити до бокса напряму. 

[secure_dns]
enabled     = true
hostname    = "dns.example.com"
certificate = "letsencrypt"   # or "files", with cert_file and key_file
devices     = ["pixel", "iphone"]
http3       = true            # DNS over HTTPS over HTTP/3 too, on UDP 443
self_setup  = "named"         # "off", "named" or "anyone"
proxies     = []              # reverse proxies whose word on the client counts

[secure_dns.acme]
cloudflare_token = "…"

DHCP

Деякі роутери не дають змінити DNS-сервер, який вони роздають. Ferrite може сам роздавати адреси, вказуючи себе DNS-сервером. У мережі має бути один DHCP-сервер, тож вимкніть його на роутері, коли вмикаєте тут. Кожен пристрій, що отримав адресу, показується під власним іменем і відповідає як name.lan. Порожні налаштування визначаються самі: адреса цього боксу, роутер і підмережа. Ferrite шукає інший DHCP-сервер так, як це зробив би новий пристрій, перед стартом і щопів години, і сторінка DHCP називає знайдені. Він ніколи не роздає адресу, якою користується інший пристрій. 

[dhcp]
enabled    = true
pool_start = "192.168.1.100"
pool_end   = "192.168.1.199"
domain     = "lan"

[[dhcp.reservations]]
mac  = "aa:bb:cc:dd:ee:ff"
ip   = "192.168.1.20"
name = "nas"

Для IPv6 оголошення роутера (RA) можуть називати цей бокс DNS-сервером, щоб пристрої не йшли повз нього. Вони оголошують лише DNS; роутером ferrite себе ніколи не пропонує.

Пароль і доступ

Вхід у браузері тримається 7 днів від останнього використання, попри перезапуски й оновлення. Налаштування → Доступ показує браузери, в яких виконано вхід, і дозволяє вийти з будь-якого; зміна пароля виводить з усіх інших.

Скрипти використовують API-ключ, переданий як Authorization: Bearer <key> або X-Api-Key: <key>. Див. довідник API.

Можна також обмежити, хто й як часто може користуватися резолвером: 

[dns]
rate_limit      = 1000                 # queries per minute per device; over it, REFUSED
allowed_clients = ["192.168.1.0/24"]   # only these get answers
denied_clients  = ["192.168.1.66"]     # these never do

Приватність і зберігання

Усе, що ви налаштовуєте, живе в config.toml. У базі лише те, що ferrite побачив сам: лог запитів, його зведення, список пристроїв і сесії панелі.

  • Зберігання: лог запитів за замовчуванням тримає 30 днів (log_retention_days), і його можна обмежити ще й у мегабайтах (log_max_mb).
  • Тільки RAM: backend = "memory" тримає історію в обмеженому кільцевому буфері в пам'яті; нічого про ваш трафік не пишеться на диск, а після перезапуску історія зникає.
  • Перемикачі: лог запитів і статистику можна вимкнути окремо. Коли вимкнено обидва, ferrite фільтрує далі й нічого не записує про те, що резолвилось.
  • Очищення логу також стискає базу, тож місце справді звільняється на диску.

Сам ferrite робить лише один запит назовні: щогодинну перевірку нового релізу на GitHub.

Оновлення

Панель показує, коли вийшов реліз, і оновлює сервер та себе на місці. Потім ferrite перезапускається з новим файлом на місці, тримаючи відкритими сокети DNS і панелі, тож жоден запит не губиться. Реліз панелі пропонується лише тоді, коли він сумісний із запущеним сервером. У Docker перезапуск контейнера теж підтягує найновіший реліз, якщо ви не закріпили версію змінними нижче.

Бекап і відновлення

Налаштування → Система експортує всю конфігурацію одним файлом і відновлює її на цьому чи іншому боксі. Копіювання config.toml робить те саме. Втративши базу, ви втратите історію й сесії, але не налаштування.

Другий бокс

Другий ferrite може слідувати за першим, тож пристрої з обома адресами отримують однакові відповіді від будь-якого. Він кожні кілька хвилин забирає з основного вибрані частини за API-ключем основного й перезапускається на місці, якщо щось змінилось, не гублячи жодного запиту. Редагуйте на основному: зміни в цих частинах на другому боксі замінюються під час наступної синхронізації. 

[sync]
primary  = "http://192.168.1.10"
api_key  = "<the primary's API key>"
interval = 300
sections = ["filtering", "records", "devices", "dns"]

Додавайте "tunnels" тільки якщо другий бокс теж маршрутизує, і ніколи з тим самим ключем WireGuard на обох: два вузли з одним ключем вибивають один одного.

З Pi-hole чи AdGuard Home

Налаштування → Система читає експорт Teleporter з Pi-hole v6 або AdGuardHome.yaml. Він показує, що перенесеться (списки, правила блокування й дозволу, локальні записи, групи й налаштування пристроїв, заблоковані сервіси) і що ні, а ви вибираєте частини ще до будь-яких змін.

Сповіщення

Один вебхук отримує подію, коли тунель лежить довше хвилини (і коли піднімається), і коли в мережі з'являється пристрій, якого бокс ще не бачив. Формат підлаштовується під отримувача: ntfy, telegram, discord, slack (також Mattermost і Rocket.Chat), gotify, або json для Home Assistant і скриптів. З налаштувань можна надіслати тестову подію. 

[notifications]
webhook       = "https://ntfy.sh/my-ferrite"
format        = "ntfy"
tunnel_alerts = true
new_device    = true

# Telegram: the bot's sendMessage URL and the chat to post to
# webhook = "https://api.telegram.org/bot<token>/sendMessage"
# format  = "telegram"
# chat_id = "123456789"

Метрики

Метрики Prometheus доступні на /api/metrics, за API-ключем, якщо він заданий. Є дашборд для Grafana — готовий до імпорту.

AI-асистенти

/api/mcp дає асистенту, що вміє Model Context Protocol (наприклад, Claude Code), бачити, що робить ferrite: чому сайт заблоковано, що робив пристрій. Він працює з API-ключем і за замовчуванням вимкнений. Для змін (блокування, дозвіл, пауза) потрібен ще один перемикач. 

[mcp]
enabled       = true
allow_changes = false

Файл конфігурації

~/.config/ferrite/config.toml для встановлення від користувача, /etc/ferrite/config.toml для всієї системи. Основний редактор — панель, вона сама записує файл; правити вручну можна, але коментарі в розділах, якими керує панель, не переживають збереження. Без файлу ferrite стартує зі звичайними upstream-серверами й панеллю на 127.0.0.1:8080. Кожен ключ описано в config.toml.example.

Порти й шляхи

Порт Для чого
53 UDP і TCP DNS
80 TCP панель і API, а також HTTP через тунель
443 TCP HTTPS через тунель, коли маршрутизацію ввімкнено, і DNS over HTTPS
443 UDP DNS over HTTP/3, коли шифрований DNS увімкнено
853 TCP DNS over TLS, коли шифрований DNS увімкнено
67 UDP DHCP, коли його ввімкнено
У теці даних Що зберігає
ferrite.db лог запитів, зведення, список пристроїв, сесії
blocklist.fst, allowlist.fst скомпільовані списки, перебудовуються, коли списки змінюються
lists/, allowlists/ розібраний кеш кожного списку
state.bin кеш і лічильники для теплого перезапуску

Тека даних: ~/.local/share/ferrite за замовчуванням і /var/lib/ferrite для інсталятора й Docker.

Змінні Docker

Змінна Що робить
FERRITE_SERVER_VERSION закріплює реліз сервера, наприклад 0.2.0
FERRITE_WEB_VERSION закріплює реліз панелі; за замовчуванням як у сервера

Розв'язання проблем

Порт 53 уже зайнятий

На Debian і Ubuntu його тримає systemd-resolved. Скрипт встановлення вимикає його stub listener; вручну задайте DNSStubListener=no у /etc/systemd/resolved.conf.d/ferrite.conf і перезапустіть systemd-resolved.

Усі пристрої видно як один

Ferrite бачить усі запити з однієї адреси: він за Docker bridge, або роутер сам пересилає DNS. Запускайте Docker у мережі host і роздавайте адресу ferrite через DHCP, а не вказуйте її upstream-сервером роутера.

Замість імен пристроїв видно IP-адреси

Зворотні запити не доходять до роутера. Виконайте ferrite setup, або додайте локальні зони вручну.

fe.te не відкривається

Пристрій ще не користується ferrite як DNS, або ferrite працює в Docker bridge без FERRITE_PANEL_IP. Поки що відкривайте адресу боксу.

Сайт чи застосунок перестав працювати

Знайдіть його в лозі запитів, клікніть заблоковане ім'я, щоб побачити, що спрацювало, і дозвольте його. Щоб швидко виключити ferrite, поставте фільтрацію на паузу для цього одного пристрою.

Тунелі повільні на малій платі

Гляньте в лозі запуску, який бекенд WireGuard вибрано. Якщо userspace, дайте ferrite CAP_NET_ADMIN і завантажте модуль wireguard у ядро. Тоді межею буде швидкість шифрування процесора, а не ferrite.
