Network control

One network, each device its own rules

Ferrite filters everything that asks it, holds the devices that need it to stricter rules, and sends what should leave privately through a tunnel. The hot path is small enough for a Raspberry Pi.

Rules per device

Profiles for the devices that need them: block TikTok or Roblox in one click, run on a weekly schedule, force SafeSearch and YouTube Restricted Mode, or allow only what you list.

Smart blocklists

Hosts, Adblock and plain lists, for blocking and allowing alike, merge into one fast lookup. Every verdict names the list, rule or service behind it.

Encrypted upstreams

Plain, DoH, DoT and DoQ in one pool with failover. Queries can ride the tunnel too, with client subnet stripped and DNSSEC requested.

Encrypted DNS on the go

Phones and laptops keep your filter on mobile data: DNS over TLS for Android, DNS over HTTPS and HTTP/3 for the rest, DNS over QUIC for apps that speak it. A QR code sets a device up, and ferrite gets the certificate itself.

See every device

What each device asked for, what was blocked and why, the services behind it and the profile in charge, one click from the live query log. When a block seems to break an app, the dashboard says so.

Alerts & automation

A tunnel down or a new device on the network reaches you on ntfy, Telegram or Discord. Everything else is a REST API, Prometheus metrics and an MCP endpoint.

Selective per-device routing

Send a domain, or a whole device chosen by its name, through a tunnel. Everything else resolves direct at full speed.

Built-in tunnels

WireGuard, SOCKS5, and Tor egress live in the resolver itself. WireGuard runs kernel-backed for line-rate throughput, or fully in-process where that isn't available. No TUN device and no root either way.

DPI evasion

Split the TLS ClientHello at the SNI across TCP segments, so middleboxes that match on hostname never see the whole name.

Custom DNS

Local A, AAAA, and CNAME records support exact and wildcard domains, so internal services get clean names.

DHCP when the router won't

If the router won't let you change its DNS, ferrite hands out the addresses itself, notices other DHCP servers on the network, and tells IPv6 devices to ask it too.

Routes that travel

A phone away from home still sends the sites you route through your tunnel. Only your own devices get in, and only for the names you chose.

Privacy

What it learns stays on the box

A DNS server sees every name your household looks up. Ferrite keeps that to itself, and lets you decide how much of it to keep at all.

No telemetry

No analytics and no phone-home. The only call it makes on its own is an hourly check for a new release on GitHub; the rest are the lists and notifications you set up.

Encrypted on the way out

DoH, DoT or DoQ to the resolvers you pick. A resolver's own queries can ride a tunnel too, so your ISP sees WireGuard and nothing else.

Nothing extra upstream

EDNS Client Subnet is stripped, so the resolver never learns your subnet. DNSSEC is requested on every query.

No TLS interception

For a routed domain it reads the SNI or Host to pick the tunnel and never terminates TLS. Your browser still checks the real certificate.

Logging you can switch off

The query log and the statistics each have a switch. Turn both off and ferrite keeps filtering while recording nothing about what was resolved.

Kind to SD cards

Keep history for as many days as you like, cap it in megabytes, or keep it in RAM only so nothing about your traffic is written to disk.

Moving in

Bring your setup, then add a second box

From Pi-hole or AdGuard Home

Settings, then System, reads a Pi-hole v6 Teleporter export or an AdGuardHome.yaml. You see what comes over (lists, rules, local records, groups, per-device settings, blocked services) and what can't, before anything changes.

Two resolvers, one setup

Point a second ferrite at the first and it takes the parts you choose every few minutes: filtering, records, device names, DNS settings. Give your devices both and either one answers the same way.

One file to back up

Everything you set lives in config.toml, and the panel can export and restore it. The database only holds history, so losing it never loses your setup.

Install

Running in a few minutes

The script downloads the server and the panel, checks their checksums, and sets up a systemd or OpenRC service. Prefer containers? The image is on GHCR.

Linux / macOS release install 
curl -fsSL https://raw.githubusercontent.com/koroblabs/ferrite-server/refs/heads/main/install.sh | sudo sh
Docker (ghcr.io) 
docker run -d --name ferrite \
  --restart unless-stopped \
  --network host \
  --cap-add=NET_BIND_SERVICE \
  -v ferrite-data:/var/lib/ferrite \
  ghcr.io/koroblabs/ferrite-server:latest
1. Point your network at it

In your router's DHCP settings, set the DNS server to the ferrite box's address. Devices pick it up with their next lease. If the router won't allow it, ferrite can hand out the addresses itself.

2. Open the panel

Go to http://fe.te on your network. It is a built-in record that points at the box.

3. Set a password

Run ferrite passwd on the box before you leave the panel reachable from the network.

Why host networking in Docker

Profiles and routing rules match each device by its address. Behind a Docker bridge every query arrives from the gateway, and all your devices look like one.

Questions

Before you install

The rest is in the docs.

Do I install anything on each device?

No. Set ferrite as the DNS server in your router's DHCP settings and every device that joins uses it. Browsers with their own "secure DNS" setting skip any network DNS filter, so leave that off or set it to the system resolver. Only a device you want filtered away from home needs setting up once: a Private DNS name on Android, a profile on an iPhone or a Mac.

What happens if the box goes down?

Devices stop resolving names until it is back. Run a second ferrite that follows the first and hand out both addresses. Don't add a public resolver as the second server: devices would use it and skip filtering.

Will it run on a Raspberry Pi?

Yes. On an ARM board serving 30 devices from a 1.8-million-domain blocklist it uses about 60 MB of memory. There are static builds for aarch64 and x86_64.

Does it need root?

The installer does, to set up the service. Ferrite itself runs as its own user with the capability to bind port 53, plus the one for kernel WireGuard if you route through it.

Does it see my HTTPS traffic?

It answers DNS. Only for a domain you route through a tunnel does the connection pass through ferrite, and then it reads the hostname to pick the tunnel without decrypting anything.

What about IPv6?

The installer has it listen on IPv4 and IPv6. If your router also advertises its own IPv6 DNS server, point that at ferrite too, or devices will ask the router instead.

Is it free?

Yes. It is MIT licensed, runs on your own hardware and needs no account.
